Settings → Skills

  1. Import and edit. Upload an existing skill package, inspect its files, and edit the instructions or replace supporting files. Save each update as a revision so you can return to an earlier version.
  2. Test and select. Choose Claude or Codex and run the skill on sample assets. Show test results per revision and runner. Select a tested pair as the YouTube default. Show any unavailable tools or incompatible settings before a run.
  3. Produce and review. The job records the skill revision and runner at submission, so later settings edits apply to new jobs. The worker stages the brief and assets in an isolated workspace and returns a playable MP4 and metadata for human review.

Keep runner credentials on the server. Give skill runs access to their own job files and configured tools. The publishing feature owns account credentials and publishes only an approved draft.

Make violations fail before merge

npm run check runs ESLint, the import graph analyzer, and their regression tests. GitHub Actions runs the same command. Require the Repository checks job on the target branch.

If violations recur, a Codex hook can reject a generated patch before a supported edit tool writes it.

Codex pre-edit hook

Imports fail in CI

ESLint flags imports across src/web/ and src/server/ in both directions. The analyzer also checks indirect paths, aliases, re-exports, and type-only dependencies. Shared contracts cannot depend on either runtime.

For same-runtime feature dependencies, declare them in feature.json and use the target's public.ts. Add checks for cycles and private feature imports during setup.

Every record has one writer

Keep migrations and write queries under the owner. Limit write access to its private persistence code and check query targets against table ownership. Other features request changes through named commands.

Share design tokens through src/style/

Keep font definitions, colors, spacing, and other shared design tokens together. Keep component styles in the feature that owns them and reference the shared tokens. Add style lint checks for raw color and font-family values in feature styles.

Load user-facing text from src/i18n/

Store complete messages by locale and resolve them by key. Use parameters for dynamic values. Keep CLI flags, JSON keys, and test IDs stable. Display source material and generated drafts as content.

Lint UI text, accessibility labels, errors, and human-readable CLI output for hard-coded copy. In CI, reject unknown keys and check that supported locales have matching keys and message parameters.

Ban React useEffect

Use route loaders and actions, derived render state, event handlers, and useSyncExternalStore for external stores. Add a typed ESLint rule that traces direct, aliased, re-exported, and namespace references to React's export.

Ban comments in authored source

Add an ESLint rule that rejects parser-reported comments in authored JS, JSX, TS, and TSX. Keep design rationale in Markdown and disable inline lint configuration. Review exceptions with a named owner, precise scope, and a removal condition.

Stage 2

Find the bottleneck after publishing

Use each publication receipt to sync metrics for its provider content ID. Store the provider metric name, definition, reporting window, and last successful sync. Request read permissions for each connected account as needed and distinguish a measured zero from delayed, unavailable, or unauthorized data.

Audience charts

Compare reach and views at the same content age within a platform and format. Plot clicks and comments as parallel outcomes. On YouTube, use thumbnail CTR to inspect the title and thumbnail, and retention to see where viewers leave.

Build sequence and exit checks

  1. Repository setupRun the existing import checks in GitHub Actions and set Repository checks as required. Add feature discovery, ownership checks, shared design tokens, locale catalogs, and feature-map generation as the corresponding code lands.
  2. CLI vertical sliceSet up the runtime folders and lint rules. Run the X fixture from brief to receipt and map each command to its planned UI and observable result. Then add LinkedIn export and test the same saved video skill and assets through both SDK runners.
  3. Stage 1 releaseWire the browser to the same commands. Verify that skill edits and runner defaults survive reload and that an existing job keeps its selected revision. Demonstrate real X publishing, YouTube upload through processing, and the LinkedIn editor handoff. Verify native LinkedIn one-click publishing with a successful API publication of a full article.
  4. Stage 2 releaseSync permitted metrics for known published IDs, rerun a sync without duplicating observations, and trace a chart value to its provider and time window. Verify delayed data and a revoked connection in the dashboard.
